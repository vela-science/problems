# Vela Problems

The Next.js scientific-state and research-work application for the sole
canonical product origin, [`problems.science`](https://problems.science/).

It reads a release-bound, normalized Neon projection generated by
`@vela/projection-data` from exact canonical repository Git repositories. Neon is
a rebuildable index, not scientific custody. The application has no signer,
scientific mutation API, authority operation, or private coordination data.
Optional AuthKit accounts provide personal product identity only: they are not
Vela actors, signers, authorship records, or a path to repository authority.

## Architecture

- `src/app`: routes and route-owned composition
- `src/components/controllers`: URL and data coordination
- `src/components/vela`: Problems shell, graph, and other product-specific
  compositions
- `@vela/brand`: framework-neutral tokens, product fonts, and sail
- `@vela/ui`: shared shadcn `base-nova`/Base UI primitives and stable Vela
  presentation semantics
- `@vela/projection-data`: exact projection and read contracts

Generic primitives are installed and updated only in `packages/ui`; the
Problems does not maintain an app-local `components/ui` copy.
[`components.json`](components.json) is a consumer configuration aligned to
the shared package.

The product anatomy retains provenance to the archived Problems at
`vela-science/vela-site@34e3f20`. Scientific facts and roots do not come from
that archive.

## Human accounts

Public evidence routes remain readable without an account and deterministic at
their published release root. Authentication is isolated to `/account`,
`/api/account`, `/sign-in`, and `/auth/callback`; no session state participates
in scientific projections or their roots. Those four paths are also exactly what
`src/proxy.ts` matches, so the read-only surfaces never enter the session
proxy at all. There is no `/sign-out` route — signing out is the
`signOutAccount` Server Action in `src/app/actions/auth.ts`.

AuthKit is enabled only when all four variables are valid:

```text
WORKOS_API_KEY
WORKOS_CLIENT_ID
WORKOS_COOKIE_PASSWORD       # at least 32 characters
NEXT_PUBLIC_WORKOS_REDIRECT_URI=https://problems.science/auth/callback
GITHUB_APP_ID                  # problems.science GitHub App numeric id
GITHUB_APP_SLUG                # canonical public app slug
GITHUB_APP_PRIVATE_KEY         # RSA key; server-only, never stored in Neon
GITHUB_APP_WEBHOOK_SECRET      # at least 32 characters
```

Three settings in the [WorkOS dashboard](https://dashboard.workos.com) have to
agree with those, and nothing in this repository can assert them:

- **Redirect URI**: exactly `https://problems.science/auth/callback`. Development
  may use `http://localhost:4322/auth/callback`.
- **Sign-in URL** (`initiate_login_uri`): `https://problems.science/sign-in`.
  Without it, WorkOS-initiated flows such as impersonation cannot complete the
  PKCE verification the library enforces on every callback.
- **Logout redirect**: `https://problems.science/repositories`, which is where
  `accountReturnTo()` sends a signed-out reader.

Keep provider secrets in the deployment environment, never in a checked-in
file. An unconfigured build deliberately omits account controls and leaves the
public Problems fully available.

GitHub sign-in is enabled in the same WorkOS AuthKit application. Repository
access is deliberately separate: the **Vela Science** GitHub App requests only
Metadata read and Contents read for explicitly selected repositories. Its
one-hour installation token stays in server memory while the exact commit is
inspected and is never written to Neon, HTML, logs, or a Vela object. A manual
public `https://github.com/OWNER/REPOSITORY` import uses the identical pinned
inspection path without a GitHub identity or App installation.

The Vercel project is the one deployed runtime environment source. Do not
maintain a second `.env.local` copy of its secrets. Vercel deliberately does
not return `sensitive` values to `env pull` or `env run`; an exact local public
build therefore obtains fresh least-privilege database URLs from Neon instead
of copying production credentials:

```bash
VELA_PROJECTION_DATABASE_URL="$(neonctl connection-string main --project-id lingering-meadow-20929365 --role-name vela_projection_reader_20260813 --database-name vela_projection --pooled --no-color)" \
VELA_ACTIVITY_DATABASE_URL="$(neonctl connection-string main --project-id lingering-meadow-20929365 --role-name vela_activity_app --database-name vela_activity --pooled --no-color)" \
bun run --filter @vela/problems build
```

## Operator checks

These package scripts belong to the direct operator model rather than a workflow. They are
recorded here because a script no document names reads as dead code to the next
person sweeping the repository.

```bash
bun run --filter @vela/problems check:routes
bun run --filter @vela/problems check:deployment https://problems.science <40-hex commit>
bun run release:problems
```

`check:routes` asserts the public route contract against an existing `.next`
build. `scripts/build.mjs` already runs the same file, so this is the standalone
re-run that skips the rebuild.

`check:deployment` fetches `/.well-known/vela-site.json` from a deployment and
holds it to the exact commit: Vercel provider, present deployment id, root
`package.json` version, computed brand root, current projection manifest, and
the full `problemsDeploymentManifestSchema`. It is the canonical deployed
manifest check used by the direct operator release.
